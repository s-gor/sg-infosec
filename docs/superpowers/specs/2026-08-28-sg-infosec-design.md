# SG InfoSec — архитектурная спецификация

Дата: 2026-08-28  
Статус: утверждённый дизайн перед планированием реализации

## 1. Назначение

SG InfoSec — независимый лёгкий модуль защиты административных панелей, API и отдельных системных сервисов на Linux-сервере.

Первой интеграцией является SG-Gateway, однако ядро SG InfoSec не должно зависеть от кода, базы данных, языка программирования или схемы развёртывания SG-Gateway. Другие панели подключаются через документированный локальный протокол и собственные адаптеры.

Основная задача первой версии — обнаруживать повторяющиеся опасные события, создавать временные решения о блокировке и применять их только к тому ресурсу, который атакуется.

## 2. Основные принципы

1. **Отдельный продукт.** SG InfoSec имеет собственный репозиторий, пакеты, службы, конфигурацию, состояние и цикл обновления.
2. **Локальная работа.** Ядро не требует внешнего облака, публичного API или передачи телеметрии.
3. **Минимальные привилегии.** Анализатор работает без root. Привилегированный компонент умеет выполнять только заранее определённые операции применения решений.
4. **Структурированные события.** Интеграции передают типизированные события, а не неструктурированные строки журналов.
5. **Раздельные области защиты.** Решение для административного входа не должно блокировать VPN, подписки, публичный API или другие службы того же сервера.
6. **Безопасный отказ.** Отказ SG InfoSec не должен останавливать защищаемую панель, VPN или системные службы.
7. **Независимость от панели.** Панели не получают root-доступ и не управляют `nftables` напрямую.
8. **Предсказуемость.** В первой версии отсутствуют машинное обучение, внешняя репутация IP и автоматически загружаемые правила.

## 3. Границы первой версии

### 3.1 Входит в MVP

- приём событий от локальных приложений через Unix-сокет;
- защита административного входа;
- защита административного API;
- защита SSH на уровне `nftables`;
- скользящие временные окна и пороговые правила;
- временные блокировки;
- увеличение длительности при повторных нарушениях;
- IPv4 и IPv6;
- белые списки IP и CIDR;
- постоянное хранение решений, правил и аудита в SQLite;
- автоматическое истечение решений;
- восстановление активных решений после перезагрузки;
- CLI для диагностики и администрирования;
- прикладной middleware для проверки решений на административных маршрутах;
- первая интеграция с SG-Gateway;
- установка как набор systemd-служб на Ubuntu/Debian.

### 3.2 Не входит в MVP

- облачная консоль;
- обмен репутацией IP между серверами;
- WAF и анализ тела HTTP-запросов;
- машинное обучение;
- универсальный парсер произвольных логов;
- каталог сторонних сценариев;
- географическая аналитика;
- уведомления во внешние мессенджеры;
- Docker/Kubernetes как основной способ установки;
- замена SIEM, IDS или антивируса;
- глобальная блокировка IP по всем портам сервера.

## 4. Целевая среда первой установки

Первая тестовая установка выполняется на Ubuntu 24.04 с systemd, Nginx, SG-Gateway и `nftables`.

На сервере одновременно работают AWG2, AWG3, AWG3.1, Xray, Mihomo и административная панель. SG InfoSec не изменяет существующие таблицы `sg_gateway_awg`, `sg_gateway_awg3` и `sg_gateway_awg31` и не применяет решения к VPN-портам.

Сервер имеет ограниченный объём памяти, поэтому проект должен соблюдать следующие бюджеты:

- `sg-infosecd`: целевой RSS в простое не более 30 МиБ;
- привилегированный enforcer: целевой RSS в простое не более 15 МиБ;
- CPU в простое: практически нулевая постоянная нагрузка;
- отсутствует постоянный внешний сетевой трафик;
- история событий ограничивается сроком хранения и размером базы.

## 5. Архитектура

```text
Защищаемая панель / адаптер
        │
        │ HTTP/JSON через Unix-сокет
        ▼
/run/sg-infosec/events.sock
        │
        ▼
sg-infosecd (непривилегированный)
  ├─ проверка и нормализация событий
  ├─ движок политик
  ├─ SQLite
  ├─ решения и аудит
  └─ локальный control API
        │
        │ типизированные команды
        ▼
/run/sg-infosec/enforcer.sock
        │
        ▼
sg-infosec-enforcerd (root)
  └─ отдельная таблица nftables

Административные маршруты панели
        │
        ▼
локальный middleware → проверка активного решения
```

### 5.1 Почему нужны два способа применения решений

`nftables` различает адреса, протоколы и порты, но не различает URL-маршруты. Если административная панель и подписки доступны через один HTTPS-порт, блокировка этого порта отключит пользователю оба ресурса.

Поэтому:

- `admin-login` и `admin-api` применяются внутри панели только к защищаемым маршрутам;
- `ssh` и другие службы с отдельным портом могут блокироваться через `nftables`;
- портовая блокировка панели допустима только при явно выделенном административном порте;
- интеграция SG-Gateway по умолчанию использует прикладной middleware для административных маршрутов.

## 6. Компоненты

### 6.1 `sg-infosecd`

Основной демон, написанный на Go.

Обязанности:

- принимать события;
- определять источник по Unix peer credentials, а не по заявленному клиентом имени;
- проверять схему и допустимый размер сообщения;
- нормализовать IP через `net/netip`;
- применять правила и обновлять счётчики;
- создавать, продлевать, отзывать и завершать решения;
- хранить состояние в SQLite;
- предоставлять локальный API для middleware и CLI;
- отправлять только допустимые команды enforcer;
- повторять применение решений после временного отказа enforcer;
- выполнять очистку старых событий и аудита по политике хранения.

Демон запускается от отдельного пользователя `sg-infosec` и не имеет прав на изменение firewall.

### 6.2 `sg-infosec-enforcerd`

Минимальный привилегированный демон.

Обязанности:

- создать и проверить отдельную таблицу `inet sg_infosec`;
- применять и удалять элементы только в заранее определённых наборах;
- принимать только команды `ensure`, `add`, `remove`, `list` и `reconcile`;
- отклонять неизвестные scope, протоколы, порты и некорректные IP;
- работать через netlink-библиотеку, без shell-команд и конкатенации пользовательских строк;
- вести отдельный системный журнал операций.

Enforcer не читает базу панели, не обрабатывает HTTP-события и не принимает соединения из сети.

### 6.3 `sg-infosecctl`

Локальная командная утилита.

Минимальные команды:

```text
status
health
sources list
policies list
policies validate
events list
decisions list
decisions add
decisions revoke
allowlist list
allowlist add
allowlist remove
audit list
nft reconcile
```

Изменяющие команды доступны только root или членам отдельной административной группы.

### 6.4 Интеграционный SDK и адаптеры

Ядро публикует стабильный протокол, а не требует использования конкретной библиотеки.

Первая поставка содержит:

- Go-клиент;
- минимальный Python-клиент;
- адаптер SG-Gateway;
- спецификацию протокола для PHP, Node.js и других языков.

Адаптер панели выполняет две независимые функции:

1. отправляет структурированные события;
2. проверяет активное решение перед выполнением защищаемого маршрута.

## 7. Локальные интерфейсы

### 7.1 Сокеты

```text
/run/sg-infosec/events.sock
/run/sg-infosec/control.sock
/run/sg-infosec/enforcer.sock
```

- `events.sock` доступен группе отправителей событий;
- `control.sock` доступен административной группе и middleware только в рамках разрешённых операций;
- `enforcer.sock` доступен только пользователю `sg-infosec` и root;
- сокеты создаются systemd с фиксированными владельцами и режимами;
- публичные TCP/UDP-порты не создаются.

### 7.2 Протокол

В MVP используется HTTP/1.1 с JSON через Unix domain socket. Это упрощает интеграцию с разными языками и не открывает сетевой API.

Ограничения:

- максимальный размер события задаётся конфигурацией, исходное значение 16 КиБ;
- неизвестные поля отклоняются для управляющих запросов и допускаются только внутри ограниченного `metadata` для событий;
- каждый ответ содержит машинно-читаемый код результата;
- запросы имеют идентификатор для аудита и идемпотентности;
- время передаётся и хранится в UTC.

### 7.3 Событие

```json
{
  "event_id": "01J6...",
  "event_type": "auth.failed",
  "scope": "admin-login",
  "ip": "203.0.113.10",
  "subject": "admin",
  "occurred_at": "2026-08-28T19:00:00Z",
  "metadata": {
    "reason": "invalid_password",
    "route": "/admin/login"
  }
}
```

Поле `source` не принимается как доверенное. Источник определяется сервером по UID/GID процесса и локальной конфигурации разрешений.

Запрещено передавать:

- пароль или его хеш;
- bearer-токен;
- cookie;
- приватный ключ;
- полный URL подписки с секретом;
- содержимое конфигурации клиента;
- тело запроса, если оно может содержать секреты.

## 8. Источники и доверие

Конфигурация источников связывает Unix UID/GID с логическим `source_id` и разрешёнными типами событий.

Пример логики:

```text
UID sg-gateway
  source_id = sg-gateway
  allowed_events = auth.failed, api.auth_failed, auth.succeeded
  allowed_scopes = admin-login, admin-api
```

Демон:

- игнорирует заявленную клиентом идентичность;
- не позволяет источнику создавать ручные решения;
- не позволяет одному адаптеру отправлять события от имени другого;
- ограничивает частоту событий от каждого источника;
- записывает отклонённые сообщения в агрегированную диагностику без секретных данных.

## 9. Политики и движок решений

Политика содержит:

- `policy_id`;
- `enabled`;
- `event_type`;
- `scope`;
- `threshold`;
- `window`;
- `base_duration`;
- `escalation_factor`;
- `max_duration`;
- срок сброса истории повторных нарушений;
- действие применения;
- необязательные ограничения по источнику.

Пример исходной политики:

```text
policy_id: sg-gateway-admin-login
5 событий auth.failed за 10 минут
scope: admin-login
первая блокировка: 30 минут
повторная: 2 часа
максимум: 24 часа
сброс escalation: 30 дней без нарушений
```

Правила применяются по нормализованному IP. В MVP не выполняется автоматическая агрегация по ASN, стране или подсети.

### 9.1 Состояния решения

```text
pending     создано, применение ещё не подтверждено
active      применяется
expired     завершено по времени
revoked     снято администратором
failed      не применено после исчерпания повторов
```

Для прикладных решений `active` означает, что решение доступно middleware. Для firewall-решений `active` устанавливается после подтверждения enforcer.

## 10. Области защиты и способы применения

| Scope | Типичная цель | Применение по умолчанию |
|---|---|---|
| `admin-login` | форма входа | middleware панели |
| `admin-api` | административные API | middleware панели |
| `ssh` | отдельный SSH-порт | nftables |
| `panel-port` | выделенный порт панели | nftables, только при явной конфигурации |

Произвольный новый scope не создаётся автоматически. Он должен быть объявлен администратором с конкретным backend и разрешёнными параметрами.

Для SG-Gateway запрещено связывать решения MVP со следующими потоками:

- AWG2, AWG3 и AWG3.1;
- Xray, Mihomo и sing-box;
- получение подписок;
- клиентские проверки доступности;
- SMART-переключение и failover;
- обычные переподключения VPN;
- ошибки удалённых или устаревших профилей.

## 11. `nftables`

SG InfoSec владеет только таблицей:

```text
inet sg_infosec
```

Минимальный набор объектов:

```text
set ssh_v4       type ipv4_addr; flags timeout
set ssh_v6       type ipv6_addr; flags timeout
set panel_v4     type ipv4_addr; flags timeout
set panel_v6     type ipv6_addr; flags timeout
chain input      type filter hook input
```

Конкретные правила создаются из проверенной конфигурации scope. Порты не выводятся из входящих событий.

Требования:

- существующие таблицы других приложений не изменяются;
- правила имеют уникальные комментарии и версию схемы;
- IPv4 и IPv6 поддерживаются одинаково;
- используются timeout-элементы наборов, а SQLite остаётся источником истины;
- при запуске выполняется reconciliation базы и фактических наборов;
- удаление пакета удаляет только таблицу, которой владеет SG InfoSec;
- неизвестные существующие объекты внутри таблицы приводят к безопасной остановке reconciliation, а не к их удалению.

## 12. Прикладное применение решений

Middleware панели вызывает локальную проверку только на защищаемых маршрутах.

Запрос содержит:

- scope;
- нормализованный адрес клиента;
- идентификатор маршрута;
- request ID.

Ответ:

```json
{
  "blocked": true,
  "decision_id": "01J6...",
  "expires_at": "2026-08-28T19:30:00Z",
  "reason_code": "threshold_exceeded"
}
```

Требования:

- короткий локальный timeout;
- небольшой кэш решений в адаптере;
- при недоступности SG InfoSec административный маршрут работает в режиме fail-open;
- отказ фиксируется в журнале панели с ограничением частоты сообщений;
- middleware не применяется к подпискам, VPN и публичным маршрутам;
- разблокировка вступает в силу без перезапуска панели.

## 13. Определение реального IP

SG InfoSec не интерпретирует `X-Forwarded-For` самостоятельно. Реальный адрес определяет интеграция панели на основе явного списка доверенных reverse proxy.

Для SG-Gateway:

- непосредственный peer должен быть доверенным Nginx на локальном интерфейсе;
- используется только настроенная цепочка trusted proxy;
- произвольный клиентский `X-Forwarded-For` не считается достоверным;
- адрес нормализуется до передачи события и повторно проверяется ядром;
- отсутствие достоверного адреса приводит к отказу от автоматического решения, а не к блокировке proxy-адреса.

## 14. Хранение данных

SQLite работает в WAL-режиме.

Основные таблицы:

- `schema_migrations`;
- `sources`;
- `policies`;
- `events`;
- `event_counters`;
- `decisions`;
- `decision_attempts`;
- `allowlist_entries`;
- `audit_log`.

Требования:

- внешние ключи включены;
- миграции выполняются транзакционно;
- операции создания решения и записи аудита атомарны;
- события имеют ограниченный срок хранения;
- решения и административный аудит хранятся дольше событий;
- база имеет ограничение размера и обслуживается без длительной блокировки;
- резервная копия выполняется через SQLite backup API, а не копированием активного WAL-набора.

## 15. Белый список

Поддерживаются:

- отдельный IPv4/IPv6;
- CIDR;
- необязательное ограничение по scope;
- обязательное описание причины;
- необязательное время истечения.

Приоритет белого списка выше автоматической политики, но ниже явного ручного решения администратора, если ручная команда содержит подтверждение обхода allowlist.

Защитные значения по умолчанию:

- loopback всегда разрешён для локальных API;
- адрес активной административной сессии не добавляется автоматически в постоянный allowlist;
- при ручной блокировке собственного адреса CLI требует явного подтверждения;
- частные диапазоны не разрешаются автоматически, поскольку администратор может входить через публичный reverse proxy.

## 16. Отказы и восстановление

### 16.1 Недоступен `sg-infosecd`

- панели продолжают работу в fail-open;
- новые события временно теряются или буферизуются адаптером в пределах малого лимита;
- существующие firewall-решения продолжают действовать до timeout;
- systemd перезапускает демон;
- после запуска выполняется reconciliation.

### 16.2 Недоступен enforcer

- прикладные решения продолжают работать;
- firewall-решения остаются `pending`;
- демон повторяет применение с ограниченным backoff;
- VPN и панель не останавливаются;
- состояние отражается в health и CLI.

### 16.3 Повреждена SQLite

- демон не создаёт новые решения;
- база не удаляется и не пересоздаётся автоматически;
- служба переходит в degraded/failed health;
- существующие firewall timeout-решения остаются до истечения;
- восстановление выполняется из проверенной резервной копии или административной процедурой.

### 16.4 Несовпадение базы и firewall

SQLite является источником истины. Reconciliation:

1. проверяет принадлежность таблицы SG InfoSec;
2. добавляет отсутствующие активные элементы;
3. удаляет только известные SG InfoSec элементы без активного решения;
4. не затрагивает чужие таблицы и неизвестные объекты;
5. фиксирует результат в аудите.

## 17. Безопасность systemd-служб

Для непривилегированного демона применяются:

- отдельный пользователь и группа;
- `NoNewPrivileges=yes`;
- `PrivateTmp=yes`;
- `ProtectSystem=strict`;
- `ProtectHome=yes`;
- ограниченный `ReadWritePaths`;
- запрет сетевых address families, кроме `AF_UNIX`;
- `CapabilityBoundingSet=` без capabilities;
- фильтрация системных вызовов после проверки совместимости.

Для enforcer:

- отдельная root-служба;
- минимальный filesystem access;
- только `AF_UNIX` и netlink;
- минимальный capability set, достаточный для `nftables`;
- отсутствие shell и запуска внешних пользовательских команд;
- строгий протокол и лимиты сообщений.

## 18. Конфигурация

Основной каталог:

```text
/etc/sg-infosec/
```

Предлагаемые файлы:

```text
sg-infosec.yaml
sources.d/*.yaml
policies.d/*.yaml
scopes.d/*.yaml
```

Конфигурация проходит полную проверку до применения. Некорректное обновление не заменяет последнюю рабочую конфигурацию.

CLI предоставляет `config validate`. Перезагрузка конфигурации атомарна: новая версия сначала разбирается и проверяется, затем заменяет активную.

## 19. Установка, обновление и удаление

Основной формат поставки для MVP — Debian package для Ubuntu/Debian.

Пакет создаёт:

```text
/usr/bin/sg-infosecd
/usr/bin/sg-infosecctl
/usr/libexec/sg-infosec-enforcerd
/etc/sg-infosec/
/var/lib/sg-infosec/
/run/sg-infosec/
```

Требования к обновлению:

- миграции схемы выполняются до запуска новой версии;
- при неуспехе миграции старая база сохраняется без изменения;
- последняя рабочая конфигурация сохраняется;
- firewall reconciliation выполняется после успешного старта;
- интеграционные адаптеры имеют версию протокола и проверяют совместимость.

Требования к удалению:

- удаляется только принадлежащая SG InfoSec таблица `inet sg_infosec`;
- чужие firewall-правила не изменяются;
- обычное удаление сохраняет `/var/lib/sg-infosec` и конфигурацию;
- purge удаляет состояние только по явной команде;
- удаление SG InfoSec не останавливает SG-Gateway и VPN-службы.

## 20. Резервное копирование

Резервная копия содержит:

- согласованный snapshot SQLite;
- конфигурацию;
- версию формата;
- checksum-манифест.

Не требуется сохранять фактический dump `nftables`: активные элементы восстанавливаются из решений SQLite.

Восстановление:

- проверяет формат и checksum;
- выполняется при остановленном `sg-infosecd`;
- не изменяет чужие firewall-таблицы;
- после старта выполняет reconciliation;
- старые backup без необязательных новых секций должны обрабатываться через версионированные миграции.

## 21. Интеграция SG-Gateway

Первая интеграция состоит из четырёх частей:

1. отправка событий `auth.failed`, `api.auth_failed` и связанных безопасных событий;
2. middleware на административных маршрутах;
3. локальный административный API SG-Gateway для просмотра состояния SG InfoSec;
4. раздел панели «Безопасность» без прямого доступа к root-компоненту.

Панель отображает:

- состояние служб;
- события;
- активные решения;
- белый список;
- политики;
- журнал административных действий.

Все изменяющие операции панели:

- требуют авторизации администратора;
- защищены от CSRF;
- передаются через control API;
- записываются в аудит с actor, request ID и результатом.

SG-Gateway не читает SQLite напрямую и не изменяет `nftables` напрямую.

## 22. Тестирование

### 22.1 Unit

- нормализация IPv4/IPv6;
- скользящее окно;
- escalation;
- allowlist;
- истечение решений;
- проверка схемы событий;
- peer credential mapping;
- ограничения scope;
- идемпотентность;
- миграции SQLite.

### 22.2 Integration

- HTTP/JSON через Unix-сокеты;
- права файлов и сокетов;
- демон не может изменять firewall напрямую;
- enforcer принимает только разрешённые операции;
- создание и снятие `nftables`-элементов;
- reconciliation после рестарта;
- работа IPv4 и IPv6;
- fail-open middleware;
- восстановление из backup;
- обновление схемы.

### 22.3 SG-Gateway contract tests

- пять ошибок входа создают решение только `admin-login`;
- заблокированный IP не входит в административный маршрут;
- тот же IP продолжает получать подписку;
- тот же IP продолжает использовать AWG2/AWG3/AWG3.1 и другие VPN-протоколы;
- обычные reconnect/failover события не создают security event;
- поддельный `X-Forwarded-For` не блокирует чужой адрес;
- отказ SG InfoSec не останавливает панель;
- разблокировка действует без рестарта;
- UI не получает root-доступ.

### 22.4 Packaging and system tests

- чистая установка Ubuntu 22.04 и 24.04;
- update и rollback;
- uninstall и purge;
- отсутствие изменений чужих `nftables`-таблиц;
- systemd hardening;
- работа при 1 ГиБ RAM;
- длительный тест очистки SQLite;
- повторная установка после удаления.

## 23. Наблюдаемость

Health содержит:

- состояние базы;
- состояние enforcer;
- возраст последнего успешного reconciliation;
- число pending/failed решений;
- размер базы;
- число отклонённых событий по причинам;
- версию протокола.

Метрики MVP доступны локально через control API и CLI. Публичный metrics endpoint не создаётся.

Журналирование:

- структурированные записи в journald;
- отсутствие секретов;
- ограничение повторяющихся ошибок;
- отдельный audit log для административных операций;
- понятные коды причин, пригодные для UI.

## 25. Этапы реализации

1. Каркас Go-проекта, CI, конфигурация и модели.
2. SQLite, миграции и аудит.
3. Events API и peer credential mapping.
4. Policy engine и lifecycle решений.
5. Control API и CLI.
6. Enforcer и отдельная таблица `nftables`.
7. Middleware/SDK.
8. Интеграция SG-Gateway без UI.
9. Раздел «Безопасность» в SG-Gateway.
10. Debian packaging, install/update/uninstall/backup.
11. Нагрузочные, отказоустойчивые и системные тесты.

Каждый этап должен завершаться тестами и проверяемым контрактом. SG-Gateway интегрируется только после стабилизации локального протокола ядра.

## 26. Критерии готовности MVP

MVP считается готовым, когда одновременно выполнено следующее:

- SG InfoSec устанавливается на чистую Ubuntu поддерживаемой версии;
- не открывает публичный порт;
- создаёт и снимает решения по структурированным событиям;
- `admin-login` блокируется только внутри административных маршрутов;
- SSH-решения применяются через отдельную таблицу `nftables`;
- AWG2, AWG3, AWG3.1, Xray, Mihomo и подписки не затрагиваются;
- IPv4 и IPv6 проходят contract tests;
- отказ любого компонента SG InfoSec не останавливает SG-Gateway или VPN;
- после перезапуска состояние согласуется автоматически;
- update, backup, restore и uninstall проходят системные тесты;
- ресурсные бюджеты соблюдаются на тестовой VM с 1 ГиБ RAM;
- все административные изменения доступны в аудите.

## 27. Решения, зафиксированные этой спецификацией

- отдельный продукт и отдельный репозиторий;
- Go как язык ядра;
- SQLite как постоянное хранилище;
- HTTP/JSON через Unix-сокеты;
- два процесса с разделением привилегий;
- приложение-level enforcement для общих HTTPS-портов;
- `nftables` только для отдельных сервисных портов;
- локальная работа без обязательного облака;
- SG-Gateway как первая, но не единственная интеграция;
- строгий запрет на влияние решений панели на VPN и подписки.
